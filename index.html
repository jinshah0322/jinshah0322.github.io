01 · Statistical Process Control Analytics Engine

A statistical process control engine with auditable formulas

A FastAPI service that computes capability indices, control-chart rule violations and out-of-spec findings, with a step-by-step audit trail for every number.

  • Python
  • FastAPI
  • NumPy
  • SciPy
  • PostgreSQL
  • Analytics

The problem

A quality-analytics platform for regulated manufacturing needed statistics that users could trust and auditors could inspect. Formulas varied by site and had to be editable without a redeploy. Specification limits varied by market and by customer. Results needed to be explainable, not just correct.

What I built

  • A formula engine where formulas are stored in the database and evaluated in a restricted namespace, with recursive dependencies between formulas
  • An AST-based decomposition that records inputs, the substituted expression, intermediate values and the dependency tree for each calculation
  • Capability indices (Cp, Cpk, Cpu, Cpl, Pp, Ppk) with one-sided fallbacks and validation that rejects a calculation with no specification limit
  • A vectorised control-chart rule engine driven by JSONB conditions, so built-in rules and company-defined rules share one code path
  • Out-of-spec and out-of-trend analytics with overall, market and customer scope, resolved by a pure function that applies overrides over global limits
  • Stability shelf-life prediction using linear regression and a confidence bound

How it works

  1. Client request enters through the API gateway
  2. SPC service loads parameter configuration and batch data
  3. Spec resolver picks limits by scope (overall, market or customer)
  4. Formula engine evaluates the dependency chain in a restricted namespace
  5. Rule engine checks control-chart patterns using stored JSONB conditions
  6. Result row is persisted and the audit trail is returned with the numbers

Engineering decisions

  • Formulas live in the database, not in code, because sites differ and changes must not need a release.
  • The spec resolver is a pure function, because scope and override logic is easy to get subtly wrong and a pure function is easy to test exhaustively.
  • Near-zero values are snapped and NaN or Inf values are sanitised before serialisation, because a single bad number should not break a whole response.

My role

Owned this service end to end: design, implementation and tests.

Stack

  • Python
  • FastAPI
  • NumPy
  • SciPy
  • PostgreSQL
  • Hasura
  • pytest

Outcome

The platform gets calculations that carry their own explanation, can be adapted per site without code changes, and behave predictably on messy real-world data.

02 · AI Schema Builder from Word Documents

Turning Word templates into validated form schemas with an LLM

A pipeline that reads a Word document's structure, fans out LLM calls per section, validates and repairs the results, and hands a proposal to a human reviewer.

  • LLM
  • Celery
  • JSON Schema
  • Document AI
  • FastAPI

The problem

Customers had paper-style templates in Word and needed them as structured digital forms. Doing this by hand was slow, and a single large LLM call over a whole document was unreliable and hard to validate.

What I built

  • Extraction of the heading tree directly from Word styles and numbering, with no OCR needed
  • Chunking of each section so every LLM call stays small
  • A Celery chord that runs one LLM task per section in parallel, then a finalize step that merges the fragments
  • Output restricted to a fixed seven-block vocabulary and validated against JSON Schema Draft-7
  • One feedback retry, deterministic repair, and a plain-text fallback when output cannot be fixed
  • Credit gating before each call, a reviewer proposal step, and a PDF preview

How it works

  1. User uploads a .docx directly to object storage
  2. Orchestrator task extracts the heading tree and chunks sections
  3. Celery chord fans out one LLM task per section
  4. Each task gates credits, calls the model and validates against Draft-7
  5. On failure: feedback retry, then deterministic repair, then plain-text fallback
  6. Finalize task merges fragments into one schema
  7. A proposal is stored for human review and approval

Engineering decisions

  • A fixed block vocabulary is used because it makes output validatable and keeps the model from inventing structure.
  • Work is split per section, because small calls fail independently, run in parallel and cost less to retry.
  • A plain-text fallback exists so a section the model cannot handle still produces something a reviewer can fix.

My role

Owned and built this module end to end: design, implementation and tests.

Stack

  • Python
  • FastAPI
  • Celery
  • RabbitMQ
  • Azure OpenAI
  • jsonschema
  • python-docx
  • MinIO

Outcome

Reviewers start from a mostly complete, schema-valid draft instead of a blank form, and every generated schema passes validation before a human sees it.

03 · OCR-to-LLM Extraction with Human Review

Extracting structured records from scanned documents, with review

A page-parallel OCR and LLM pipeline with a mapping cascade that reduces model calls and learns from reviewer corrections.

  • OCR
  • LLM
  • Celery
  • RabbitMQ
  • SSE
  • Document AI

The problem

Scanned batch records had to become structured rows in a database. Files were large, extraction errors were costly, and users needed to see progress and confirm results rather than trust them blindly.

What I built

  • Presigned direct-to-storage uploads so large files never pass through the API
  • A PDF split worker that renders pages and creates all job rows before any OCR task is enqueued
  • One OCR task and one LLM extraction task per page, with atomic batch completion
  • Bounding-box source lookup so each extracted value can be located on the page
  • A mapping cascade (exact match, learned mapping, then batched LLM) that cuts model calls, with reviewer corrections feeding back
  • SSE progress and a confirm step that writes rows only after review

How it works

  1. Browser requests a presigned URL and uploads straight to storage
  2. Confirm call verifies the object exists and queues a split job
  3. Split worker renders pages and creates job rows
  4. OCR task runs per page
  5. LLM extraction task runs per page and returns validated JSON
  6. Mapping cascade resolves fields; batch completes atomically
  7. Reviewer confirms; rows are written; progress is streamed throughout

Engineering decisions

  • Job rows are created before tasks are queued, so progress is accurate and nothing is lost if a worker dies.
  • The mapping cascade tries cheap exact matches first, because most fields do not need an LLM.
  • Credit exhaustion is never retried, because retrying a quota error only wastes time.

My role

Owned the data capture module that includes this flow; designed and built the extraction and mapping logic. Worked alongside the team on shared infrastructure.

Stack

  • Python
  • FastAPI
  • Celery
  • RabbitMQ
  • Redis
  • Azure Document Intelligence
  • Azure OpenAI
  • MinIO

Outcome

Users get faster, traceable digitisation with a human decision point, and the system gets cheaper and more accurate as corrections accumulate.

04 · Async Report Generation and Signed Delivery

Generating large reports in the background and delivering them safely

A queue-driven pipeline that builds Word, PDF and Excel outputs and emails recipients expiring, signed download links.

  • RabbitMQ
  • FastAPI
  • DOCX
  • Security
  • Async

The problem

Annual quality reports are long, data-heavy documents. Building them inside a web request was not an option, large attachments are unreliable by email, and a failed job must never silently disappear.

What I built

  • An API that returns 202 only after the job is durably enqueued
  • Job context in Redis, with the full payload held in object storage
  • A consumer that builds the document through an HTML-to-DOCX engine with a pre-warmed LibreOffice pool and memory limits
  • Excel annexures that shrink large documents
  • Content-addressed artifacts and HMAC-signed, expiring, revocable download links with an audit log
  • Header-counted retries and idempotent consumers

How it works

  1. UI calls the API; context goes to Redis and payload to object storage
  2. Job is published durably, then the API returns 202
  3. Report consumer builds DOCX, optional PDF and Excel annexures
  4. Completion event carries a content hash
  5. Completion consumer merges annexures and packages a ZIP
  6. A signed, expiring link is created for each recipient
  7. Email worker sends the message; downloads are audit-logged

Engineering decisions

  • Enqueue happens before responding 202, because a response that outruns the queue can lose work.
  • Artifacts are content-addressed, so a redelivered message finds the existing result instead of rebuilding it.
  • Links are signed and expiring, because emailing large files as attachments is fragile and hard to revoke.

My role

Owned the new report generation module and its delivery path.

Stack

  • Python
  • FastAPI
  • RabbitMQ
  • aio-pika
  • Redis
  • MinIO
  • python-docx
  • LibreOffice
  • Node.js (email worker)

Outcome

Large reports ship reliably, retries are safe, and recipients get secure links that can be expired and traced.

05 · RAG and Self-Correcting Text-to-SQL Assistant

A regulatory-compliance chat assistant that answers from documents and a database

A streaming chat service that routes each question to retrieval or SQL, validates generated queries, and cites its sources.

  • RAG
  • Text-to-SQL
  • FastAPI
  • Streaming
  • LLM

The problem

Users needed natural-language answers over both a document corpus and a structured regulatory database. Answers had to be fast, grounded in sources and safe to run against real data.

What I built

  • A streaming chat endpoint emitting NDJSON, with a bounded queue, semaphores and Redis-based stop control
  • An LLM router that sends each question down the right path, with strict JSON output, timeouts and a safe default
  • Hybrid retrieval with semantic reranking and citation extraction, with a fallback when the ranker is unavailable
  • Text-to-SQL across three instances, with EXPLAIN validation and error feedback to the model before execution
  • Read-only SQL execution paths and failure audit rows for later review

How it works

  1. Request enters with a bounded queue and concurrency limit
  2. Language detection and optional translation
  3. LLM router picks a path: retrieval, citation lookup or data query
  4. Retrieval path: hybrid search, rerank, extract citations
  5. SQL path: generate SQL, validate with EXPLAIN, retry with error feedback, run read-only
  6. Summary step streams the answer as NDJSON
  7. Latency metrics and failures are logged for review

Engineering decisions

  • Generated SQL is checked with EXPLAIN and corrected with the database's own error, because that catches most mistakes before any data is touched.
  • The router has a safe default path, so a routing failure still produces an answer.
  • Reranker quota exhaustion falls back automatically, so retrieval degrades instead of failing.

Contributed significantly to this team-built service, including RAG, routing, text-to-SQL and streaming work.

06 · AI Document Analysis with Lock-and-Cache De-duplication

Asynchronous document analysis that does not pay for the same LLM call twice

A pipeline that summarises uploaded documents and generates recommendations, using Redis locks and caches to avoid duplicate model calls.

  • LLM
  • OCR
  • Redis
  • RabbitMQ
  • Node.js
  • Python

The problem

Users upload inspection and compliance documents and expect summaries and corrective-action recommendations. The work is slow and expensive, and the same content is often analysed more than once.

What I built

  • An upload path that runs OCR, performs a quick LLM type check, then responds immediately
  • A claim-check pattern: payload in Redis, a small pointer message on RabbitMQ
  • A worker that summarises, enriches results through the AI service and generates recommendations under a Redis lock
  • Content-hash lock and cache layers so identical work is generated once
  • Embedding-based clustering of similar titles to reduce LLM calls
  • A separate PDF worker that forks a process per job with timeouts, then emails and cleans up

How it works

  1. Authenticated upload, then OCR
  2. LLM type check on the opening text
  3. Payload stored in Redis; pointer message queued; immediate response
  4. Worker summarises and enriches the analysis
  5. Recommendations generated under a content-hash lock with cache
  6. PDF task queued; PDF worker renders and emails
  7. Usage is logged and temporary data is cleaned up

Engineering decisions

  • A content-hash lock-and-cache is used because concurrent or repeated requests should share one result.
  • Claim-check messaging keeps queue messages small and avoids losing large payloads.
  • A recommendation failure does not block the rest of the report, so users still get a useful result.

07 · Multi-Tenant Platform Foundation

Gateway authentication, audit trails and credit metering for a multi-tenant platform

The shared foundation under several services: cookie auth at the gateway, an audited database, and an atomic ledger that meters LLM usage per company.

  • Security
  • PostgreSQL
  • Hasura
  • FastAPI
  • Observability

The problem

A platform with many services and many tenants needs one consistent way to authenticate, isolate data, record who did what and cap AI spend, without each service reinventing it.

What I built

  • A gateway that verifies cookies, refreshes sessions silently, checks a revocation list and injects tenant and user headers
  • Per-service OpenAPI specs aggregated at the gateway, and a consistent error envelope with typed error codes
  • An audited PostgreSQL and Hasura schema with generic audit triggers, role-driven permissions and idempotent migrations
  • An atomic Postgres function and immutable ledger for LLM token credits, with a pre-flight gate and capped deduction
  • Metrics and logging through Prometheus, Loki and Grafana

How it works

  1. Browser calls the gateway with a cookie
  2. Gateway asks the auth service to verify; session is refreshed if needed
  3. Revocation list is checked in Redis
  4. Gateway injects user and tenant headers and forwards the request
  5. Service reads and writes through Hasura; audit triggers record changes
  6. Before an LLM call, a credit check runs; after it, usage is deducted atomically
  7. Ledger rows give a permanent usage history

Engineering decisions

  • Credit deduction runs in one database function, because that makes it safe under concurrency and keeps the balance from going negative.
  • Migrations are written to be re-applied safely, because deployment re-applies them on restart.
  • Privileged endpoints check role from the database, not a client claim, because claims can be forged.

08 · Full-Stack Marketing Analytics SaaS

A full-stack analytics SaaS that turns marketing data into reports and answers

A multi-tenant platform that turns web-analytics and search data into cached dashboards, AI insights, scheduled reports and a grounded team chat, with an MCP server for external AI assistants.

  • Full-stack
  • FastAPI
  • PostgreSQL
  • RAG
  • MCP
  • AWS

The problem

Marketing teams and agencies juggle web-analytics, search-performance, site-health and page-speed data across separate tools, then still write insights and monthly reports by hand. They needed one multi-tenant product with per-client access control, automated reporting and answers on demand, including from the AI assistants they already use.

What I built

  • A modular FastAPI backend of about 125 endpoints, with strict router, controller, service and repository layers over async SQLAlchemy and PostgreSQL
  • Connectors and an ETL pipeline that pull Google Analytics, Search Console, page-speed and site-audit data into dashboard sections cached by property and date range
  • AI insights for each dashboard section, cached by a hash of the source data, plus SEO audits and AI-search visibility signals
  • Snapshots, branded PDF and Google Sheets exports and public share links, with a separate scheduler for daily syncs and monthly snapshots
  • A retrieval-augmented team chat over saved snapshots, streamed over SSE and fanned out over WebSockets, with a cap on concurrent LLM calls
  • An MCP (Model Context Protocol) server with 10 tools, so external AI assistants can query a user's analytics behind hashed API keys, timeouts, response truncation and a per-call audit log
  • Organisations, roles and per-property access, Google OAuth with encrypted tokens, cookie sessions with refresh rotation, and admin tools with an audited impersonation trail
  • On the frontend: scheduled sync, report snapshot comparison and PDF changes, API-key management and usage stats screens, organisation and member property-access views, and Google account reconnect and sign-in handling

How it works

  1. User signs in with Google OAuth; tokens are encrypted at rest and the session lives in HTTP-only cookies
  2. User links analytics and search properties; organisation roles decide who sees each one
  3. Scheduler or a manual sync runs the ETL connectors against the Google and site-audit APIs
  4. Dashboard sections are cached by property and date range; AI insights by a hash of their source data
  5. A snapshot is saved, then exported to PDF or Sheets or shared through a public link
  6. Chunk builder turns snapshots into a retrieval knowledge base with deterministic keys
  7. Team chat streams cited answers over SSE and WebSockets; MCP tools serve external AI assistants

Engineering decisions

  • Scheduled syncs and monthly snapshots run in a separate scheduler process, because jobs inside an API with several workers would run more than once.
  • Dashboards are cached by property and date range, and AI insights by a hash of their source data, so Google API and LLM calls are only paid for again when the data actually changes.
  • Snapshots point at the exact report rows, and chat chunks are built from them with deterministic keys, so chat answers match what the dashboard shows and rebuilds are safe to repeat.
  • External AI access goes through MCP with hashed keys, timeouts, truncated responses and an audit log, so third-party assistants get useful data without unbounded or untraceable access.

I led the backend and the full-stack delivery within a small team, and built key frontend features: scheduled sync, report snapshot comparison and PDF changes, API-key (MCP) management and usage stats screens, organisation and member property-access views, and Google account reconnect and sign-in handling.

  • PostgreSQL

  • AWS

Outcome

Live in production. Marketing teams get analytics, site health, reports and AI answers in one place with per-client access control, and can bring the same data into their own AI assistants. The platform ships with per-module handover documentation.
